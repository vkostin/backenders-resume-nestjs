# ADR 0004: Сначала объект, потом строка — компенсирующая очистка

## Статус

Принято.

## Контекст

Добавление иллюстрации или установка фото профиля требуют двух записей,
которые не могут находиться в одной транзакции: объект должен попасть в
Silo (S3), а строка метаданных — в PostgreSQL. Сбой между ними оставляет
одну из сторон несогласованной.

Две формы сбоя различаются по цене:

- **Строка без объекта**: API возвращает URL, который отдаёт 404 —
  сломанное изображение портфолио, видимое каждому посетителю.
- **Объект без строки**: неиспользуемый blob в bucket — невидим для
  клиентов, стоит несколько килобайт хранилища, удаляется очисткой
  bucket.

## Решение

Операции упорядочены так, чтобы восстановимое несоответствие было
дешёвым:

- **Добавление / замена**: сначала объект загружается в Silo, затем
  пишется строка в БД. Если запись строки падает, загруженный объект
  удаляется (best-effort компенсирующее действие).
- **Удаление**: сначала удаляется строка в БД, затем объект. Если
  удаление объекта падает, orphan логируется, а мутация всё равно
  считается успешной — её контракт («портфолио больше не ссылается на это
  изображение») уже выполнен.
- **Замена фото**: после сохранения нового ключа прежний объект
  удаляется best-effort.

## Последствия

- Худший случай — осиротевший объект в S3, но никогда — висячая ссылка
  из базы данных.
- `SEED_RESET=1` в режиме `SEED_MEDIA=full` очищает bucket, что собирает
  накопившиеся со временем orphan-объекты.
- Недоступность Silo ломает загрузки и шаг очистки при удалении, но не
  обычные чтения: read-пути строят URL из сохранённых ключей и никогда
  не вызывают S3 API.
